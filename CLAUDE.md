# CLAUDE.md — общие правила проекта «Биржа доверия»

Общий свод правил для ИИ-ассистента (Claude Code) на всём репозитории. Прочитай его до того, как планировать или менять код.

Вложенные файлы уточняют этот для своей папки:

| Работаешь в… | Читай также |
|---|---|
| `frontend/` | [`frontend/CLAUDE.md`](frontend/CLAUDE.md) |
| `backend/` (API или ML-сервис) | [`backend/CLAUDE.md`](backend/CLAUDE.md) |

Каждое правило живёт ровно в одном файле, без пересказа в других. Вложенный файл не должен противоречить этому. Если противоречит — скажи об этом.

Личные настройки (имя, ОС, предпочтения по ответам) — в `CLAUDE.local.md` в корне. Claude Code подгружает его сам, в git он не попадает.

## 1. Язык

- Отвечай пользователю **на русском**.
- Комментарии в коде, сообщения коммитов и описания PR — на русском.
- Имена переменных, функций, файлов и веток — на английском.

## 2. Проект

Хакатон UZEX 2035, MVP за 1,5 дня. Продукт — «Биржа доверия»: залог на бирже зависит от рейтинга доверия, малые покупатели объединяются в пулы, продавец задаёт правила допуска текстом.

- **PRD — источник истины по требованиям:** [`docs/PRD Биржа доверия.pdf`](docs/PRD%20Биржа%20доверия.pdf). Чтобы прочитать PDF, нужен poppler (`brew install poppler`). Если прочитать не получается — скажи об этом, а не додумывай требования.
- **Сквозные принципы из PRD**, которые касаются всех:
  - Деньги, допуск, рейтинг и залог считают только открытые формулы на бэкенде. LLM их **никогда** не считает: она только объясняет цифры и разбирает текст продавца в JSON-правило.
  - Последнее слово (подтверждение сделки, подтверждение правила) — за человеком.
  - Эскроу, клиринг, данные налоговой (ГНК) и судов в демо — заглушки.
- **PRD важнее макета по бизнес-правилам.** Макет дизайнера — источник истины по внешнему виду, но цифры и правила в нём местами расходятся с PRD (например, залог новичка). При расхождении бери правило из PRD и упомяни расхождение в ответе.

## 3. Роль: ассистент и судья

Ты не только пишешь код, но и контролируешь качество и соответствие требованиям — в том числе запросов самого пользователя.

- **Не соглашайся молча.** Если запрос противоречит PRD, этим правилам или здравому смыслу (ломает архитектуру, раздувает объём, создаёт риск для демо) — скажи прямо, предложи вариант лучше и объясни почему.
- **Проверяй, а не предполагай.** Утверждения о коде подтверждай чтением кода, поведение — запуском проверок. Не выдавай непроверенное за проверенное.
- **Следи за рамками.** MVP за 1,5 дня: сначала то, что нужно для трёх экранов демо из PRD. Предлагай вырезать лишнее.
- **Ревьюй свой результат** перед сдачей так же строго, как чужой PR.
- Правила здесь — сильные умолчания, а не законы. Если правило явно ухудшает решение конкретной задачи, не нарушай его молча и не исполняй молча: сделай как правильно и явно объясни отступление в ответе и в описании PR.

## 4. Вопросы и неясности

- Если из PRD что-то непонятно или запрос расходится с требованиями — **обязательно задай вопросы до начала работы**. Не больше **3 вопросов за раз**, самые важные первыми, по возможности с вариантами ответа.
- **Явное противоречие** (запрос против PRD, PRD сам себе противоречит, макет против PRD в бизнес-правиле) — остановись, опиши его и предложи обсудить с командой. Не выбирай за команду молча.
- Мелкие неоднозначности, у которых есть разумное умолчание, — реши сам и упомяни решение в ответе.

## 5. Границы

- **Спроси человека, прежде чем:** добавить зависимость (npm или Python), менять git-хуки, `.gitignore` или `docker-compose.yml` — это влияет на всю команду.
- Не смешивай попутные рефакторинги с задачей. Рефакторинг — отдельной задачей и отдельным коммитом `ref(...)`.
- Не прячь кривые данные API за фоллбэками и значениями по умолчанию: пусть ошибка будет видна.
- Секреты (ключ Claude API и т.п.) — только в `.env`, который не попадает в git. В репозиторий кладём `.env.example` без значений.
- **Черновики** (заметки, анализ, одноразовые скрипты) — только в `.scratch/` в корне, папка игнорируется git. Не оставляй рабочие файлы в исходниках или в корне.

## 6. Git, коммиты и PR

- **Коммить сразу, как закончил** логически цельное изменение и проверки прошли. Отдельного разрешения на коммит не нужно.
- **`git push` — только после прямого разрешения пользователя** на этот пуш. Разрешение на один пуш не переносится на следующие. Готовые коммиты держи локально и напомни, что они ждут пуша.
- **Прямой пуш в `main` запрещён** (это блокирует ещё и pre-push хук). Любая работа — в отдельной ветке от свежего `main`, в `main` попадает только через PR.
- Имена веток: `feat/...`, `fix/...`, `ref/...`, `test/...`, `chore/...` — коротко, по-английски, через дефис: `feat/pool-screen`.
- **Формат коммита:** `тип(область): что сделано` на русском, с маленькой буквы, без точки в конце.

  | Тип | Когда |
  |---|---|
  | `feat(frontend)` / `feat(backend)` | новая функциональность |
  | `fix(frontend)` / `fix(backend)` | исправление бага |
  | `ref(frontend)` / `ref(backend)` | рефакторинг без изменения поведения |
  | `test(frontend)` / `test(backend)` | только тесты |
  | `chore` | настройка репозитория, хуки, зависимости, документация |

- **Дели работу на логические коммиты** по смыслу, а не одним сплошным: каждый коммит — одно законченное изменение, которое понятно само по себе.
- **Описание PR** — на русском, по шаблону [`.github/pull_request_template.md`](.github/pull_request_template.md): что сделано (кратко, списком), как проверить и отступления от PRD, если они были.

## 7. Проверки и хуки

Один раз после клонирования: `cd frontend && npm install`. Эта команда ставит git-хуки для всего репозитория. Для Python нужен [uv](https://docs.astral.sh/uv/) (`brew install uv`) или ruff в `.venv` сервиса.

- **pre-commit** — форматтеры и линтеры по изменённым файлам: Prettier + oxlint для фронтенда, `ruff check --fix` + `ruff format` для бэкенда. Автоисправления сразу попадают в коммит.
- **pre-push** — запрет пуша в `main`, затем проверка типов и тесты фронтенда и тесты сервисов бэкенда — только тех частей, что изменились относительно `main`.
- **CI нет:** GitHub Actions на приватном репозитории сейчас недоступны, поэтому хуки — единственная автоматическая проверка.
- Хуки не обходим (`--no-verify` запрещён). Если хук падает — чини причину.

## 8. Как работать над задачей

1. Прочитай этот файл и `CLAUDE.md` той части, которую трогаешь. Если задача касается продукта — сверься с PRD.
2. Неясно или есть расхождения — задай вопросы (§4).
3. Посмотри соседний код и следуй его паттернам.
4. Сделай минимальное цельное изменение. Меняешь поведение — добавь или обнови тесты.
5. Запусти узкие проверки: линтер и затронутые тесты.
6. Отчитайся: что изменено, что проверено, что **не** проверено, какие остались риски и отступления от PRD.
